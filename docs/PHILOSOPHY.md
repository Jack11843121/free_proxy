# free_proxy 的代理理念

## 一句话

**一个本地入口，屏蔽所有上游 IP 代理供应商的差异。**

## 为什么需要它

做爬虫 / RPA / 数据采集时，几乎一定会用到「代理 IP」。你可能会同时购买多家供应商（品赞、快代理、巨量……），于是立刻遇到一长串麻烦：

1. **每家接口都不一样**：鉴权有直传 token、HMAC-SHA1、MD5 签名；返回字段有的叫 `data.list`，有的叫 `data.proxy_list`；分隔符有换行、空格、竖线。
2. **IP 会过期**：短效 IP 可能 1~5 分钟就失效，业务代码自己判断「过期」非常脆弱。
3. **IP 会被封 / 抽风**：某个 IP 突然连不上、超时，需要自动剔除并换一条。
4. **业务代码和供应商强耦合**：换供应商 = 改代码；加供应商 = 再改代码。

`free_proxy` 的思路是：把这些「供应商差异 + 生命周期管理」全部收进一层，对外只给一个**稳定、标准、自愈**的本地 HTTP 代理端口。业务代码永远只和 `127.0.0.1:8899` 打交道。

## 五条设计原则

### 1. 供应商无关（Provider-agnostic）

所有上游供应商被抽象成同一个接口：

```
fetch() -> [ {ip, port, user, password?, expire?} ]
```

无论品赞、快代理、巨量还是某个不知名小厂，对代理池来说都「只是 IP 列表的一个来源」。新增一家供应商，理想情况下**只加一段 YAML 配置，不改一行代码**（见 `generic` 适配器）。

### 2. 自愈（Self-healing）

代理 IP 是「易耗品」。free_proxy 用一个后台调度器持续做两件事：

- **健康检查**：定时通过每条代理访问一个稳定目标，记录存活和延迟；
- **淘汰与补货**：连续失败 N 次判死移除；过期 IP 清理；池子低于阈值自动向供应商批量拉新。

于是「坏 IP 被挡下、好 IP 被保留、不够了自动补」这个循环永远在跑。

### 3. 对业务透明（Transparent）

free_proxy 是一个**真代理网关**，不是「给你一个 IP 你自己配」的半成品：

- 标准 HTTP 前向代理；
- HTTPS 走 `CONNECT` 隧道；
- 字节级透明中继，不解析、不修改你的请求/响应内容。

所以现有的 `requests` / `aiohttp` / `curl` / 浏览器 / RPA 脚本，**零改动**就能用。

### 4. 可观测（Observable）

一个跑在生产里的组件，必须能回答三个问题：现在有代理可用吗？有几条是活的？哪家供应商贡献最多？

控制面 API 提供状态、代理列表、取单条 IP、手动刷新/检查，让这一切一目了然，也方便接监控告警。

### 5. 易扩展（Extensible）

三类扩展点，成本从低到高：

| 扩展点 | 成本 | 场景 |
|---|---|---|
| `generic` 模板 | 0 代码 | 大多数「URL+签名+列表字段」的代理商 |
| 新增签名算法 | 少量代码 | 某家用了特殊签名（如 RSA、国密） |
| 新增独立适配器 | 一个文件 | 接口逻辑复杂，需定制解析 |

## 与「裸用代理商」的区别

| | 直接调供应商 | 用 free_proxy |
|---|---|---|
| 换供应商 | 改代码 | 改配置 |
| 加供应商 | 改代码 + 学新 API | 加一段 YAML |
| IP 过期处理 | 自己写 | 自动 |
| 坏 IP 剔除 | 自己写重试/熔断 | 自动健康检查 |
| 多机共享 | 自己搭 | `store.backend=redis` 一行 |
| 业务代码 | 依赖供应商 SDK | 只依赖标准代理 |

## 目标用户

- 需要多供应商聚合、统一出口的爬虫 / 数据团队；
- 需要稳定代理出口的 RPA / 自动化脚本；
- 想私有化部署、不想把代理流量交给第三方转发的企业。
