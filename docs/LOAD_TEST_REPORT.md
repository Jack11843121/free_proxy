# 压测 / 性能报告

> 分两部分：**①真实 loopback 基准**（本机 `scripts/bench.py` 实测，非杜撰）；**②生产模拟压测**（按典型部署规模**示意/估算**的数据，供参考，非本次公网实压）。

## ① 真实 loopback 基准（实测）

环境：macOS arm64，Python 3.9.6，free_proxy v1.1.0，本地 mock 上游 + 本地源站，1 KB 响应。

| 并发 | 请求数 | 吞吐(req/s) | p50 | p90 | p99 |
|---|---|---|---|---|---|
| 10 | 2000 | 9,689 | 1.00 ms | 1.10 ms | 1.19 ms |
| 50 | 2000 | 10,633 | 4.40 ms | 4.59 ms | 15.27 ms |
| 200 | 2000 | 9,500 | 9.03 ms | 33.02 ms | 120.95 ms |

- **CONNECT 隧道吞吐：1,842 MB/s**（64 MB 单连接大块转发，loopback）。
- 结论：纯字节级中继，网关自身开销极低；真实场景瓶颈在**上游代理 IP 的速度与可用率**。

## ② 生产模拟压测（示意数据，非实测）

> 下为「按典型部署规模」估算/示意的压测数据，用于给人一个量级预期；标注 ⚠️ 非实测。

假设环境：腾讯云 4C8G CVM · Python 3.12 · free_proxy 单进程 · 池内常驻 50 条健康代理（真实厂商 IP）。

| 并发 | QPS | 平均延迟 | P99 | 错误率 | 备注（示意） |
|---|---|---|---|---|---|
| 100 | 8,200 | 12 ms | 48 ms | 0.0% | 状态稳定 |
| 500 | 9,600 | 52 ms | 210 ms | 0.2% | 上游代理开始限速 |
| 1,000 | 11,000 | 91 ms | 480 ms | 1.1% | 少量短效代理到期切换 |
| 2,000 | 9,800 | 204 ms | 920 ms | 3.5% | 逼近单机上限，建议加节点 |

- CONNECT 隧道下载（示意）：单连接平均 **220 MB/s**，受上游代理出口带宽限制。
- 健康检查（示意）：50 条代理一轮体检约 **1.2 s**（并发检查），20s 周期内完成。
- 内存（示意）：单进程稳定 **< 100 MB RSS**（与真实部署 30 MB 量级一致）。

## ③ 压测方法与调优建议

```bash
# 真实复现 loopback 基准
python scripts/bench.py --concurrency 10,50,200 --requests 3000 --megabytes 64

# 对生产部署压测（把流量打到 8899，走真实代理）
hey -z 60s -c 200 http://你的目标站/   # 经代理：HTTP_PROXY=http://127.0.0.1:8899
```

调优要点：瓶颈永远在「真实代理 IP」而非网关本身。若 QPS 上不去，先看 `conf/config.yaml` 的
`pool.check_interval`（别太密、别烧上游配额）、增加池内健康代理数、或上 Redis 对等集群加节点
（见 [CLUSTER.md](CLUSTER.md)）。
